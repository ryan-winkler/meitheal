# Phase 04.1: Human-Agent DDD Core — Research

**Date:** 2026-03-18
**Phase:** 04.1 — Human-Agent DDD Core
**Status:** Research complete, awaiting discuss-phase approval

---

## Executive Summary

The current Meitheal codebase still treats hierarchy and execution behavior as the same concept. `epic`, `story`, and `task` are baked into `task_type`, strategic rules, kanban swimlanes, icons, filters, API validation, and compat docs. That is the core modeling problem.

The cleanest pre-release answer is:

1. Hard-cut `Epic` and `Story`.
2. Promote `Area`, `Goal`, `Project`, and `Routine` into first-class roots or explicit relations.
3. Reduce `Task` to the atomic execution record.
4. Rename hierarchy-free task behavior to `task_kind` and use it for `standard_action`, `shopping_item`, and `checklist`.
5. Add bot-safe orchestration primitives directly to `Task`, plus an append-only `task_audit_ledger`.
6. Replace monolithic row-level last-write-wins with field-family-aware merge behavior for offline and bot collaboration.

The biggest execution risk is not the new schema itself. It is the number of places that currently assume:
- `task_type` means hierarchy
- `board_id` is the main grouping primitive
- offline sync can safely use a minimal task shape
- `/api/v1/tasks` is equivalent to `/api/tasks`

## Current-State Findings

## 1. There are two task schema truths today

`apps/web/drizzle/schema.ts` is still a narrow integration/event schema. The live application task schema is actually created and migrated in `apps/web/src/domains/tasks/persistence/store.ts`.

Implication:
- Any execution phase that changes the task model must touch both files.
- Proposing only a `drizzle/schema.ts` diff is not enough for real implementation, but it is still useful as the clean target contract.

## 2. `task_type` is overloaded everywhere

Hierarchy terms are not isolated to persistence. They drive:
- domain types in `packages/domain-tasks/src/task.ts`
- strategy presets in `packages/domain-strategy/src/rule-types.ts`
- settings rules UI in `SettingsRules.astro` and `settings-rules-controller.ts`
- task creation/update validation in `/api/tasks`
- visual identity in `type-icon-config.ts`
- filters, swimlanes, search, gantt, kanban, and task detail UI

Census:
- `epic` / `story` references exist across 25+ files in `apps/web` and `packages`
- `board_id` / board semantics exist across 35+ files
- `checklists`, `parent_id`, `task_type`, or subtask assumptions exist across 40+ files

Implication:
- Keeping `Goal` and `Project` as renamed `task_type` values would preserve the exact problem we are trying to solve.

## 3. Boards are a UI/runtime grouping, not a clean domain abstraction

Today, `board_id` is the primary organizational field on tasks and powers:
- board filtering
- sidebar board switcher
- board API routes and repository
- search results
- HA events and outbound integrations
- Grocy and Todo sync defaults

At the same time, `vikunja-compat` already has its own `project_id` side-table model in `vikunja_task_meta`.

Implication:
- `board_id` cannot remain the only grouping primitive if `Project` and `Area` become real domain objects.
- Compatibility wants `Project`.
- Human life-planning wants `Area`.

## 4. Offline support is too thin for bot-aware collaboration today

`apps/web/src/domains/offline/offline-store.ts` only stores:
- `id`
- `title`
- `description`
- `status`
- `dueDate`
- `updatedAt`
- `createdAt`
- `syncedAt`

The sync queue stores whole payload strings and deduplicates by entity at row level.

`apps/web/src/domains/offline/sync-engine.ts`:
- assumes whole-row last-write-wins
- handles `409`
- expects server to return `updatedAt`
- writes to `/api/v1/${op.table}`

But the richer optimistic-locking path is in `/api/tasks/[id].ts`, not `/api/v1/tasks/:id`.
There is no general `PUT /api/v1/tasks/:id` route in this repo.

Implication:
- The current offline layer is not ready for split-brain human/bot edits.
- Before bot scratchpads or review payloads can be trusted offline, sync must move to the canonical `/api/tasks` contract and become patch-family aware.

## 5. HA Todo sync currently writes flat tasks directly

`todo-bridge.ts` directly inserts or updates task rows, setting fields like:
- `title`
- `status`
- `due_date`
- `description`
- `labels`
- `board_id`
- `task_type`

It does not normalize into a richer semantic layer first.

Implication:
- This is the right place to add a normalization seam, but not the right place to embed every translation rule inline.
- A shared normalization helper is needed so HA todo, Vikunja, Trello, and future bot imports can all target the same task input contract.

## 6. Vikunja compatibility already hints at the future model

`vikunja-compat/store.ts` already separates:
- Meitheal task row
- compat side-table `vikunja_task_meta` with `project_id`, `description`, `due_date`, `priority`, `repeat_after`

Implication:
- Vikunja `project` maps more cleanly to internal `Project` than to current `board`.
- The compat layer is already doing translation; we should make that translation semantically correct instead of overloading `board_id`.

## Recommended Ubiquitous Language

## Strategic Horizon

### `Area`
Durable domain of life or work.
Examples:
- `Household`
- `Coolock Village`
- `Health`
- `Meitheal`

### `Goal`
Continuous or long-horizon aspiration.
Examples:
- `Improve Health`
- `Reduce monthly grocery spend by 15%`
- `Ship Meitheal v1`

### `Project`
Finite outcome with a completion state.
Examples:
- `Kitchen Renovation`
- `Integrate Node-RED`
- `v1.0 Release`

## Orchestration Hub

### `Task`
Atomic unit of execution and delegation.
Never the place to encode strategic hierarchy via `task_type`.

### `Routine`
Cadence/template/anchor that spawns or validates tasks.

## Execution Kind

Use `task_kind`, not `task_type`, for execution behavior:
- `standard_action`
- `shopping_item`
- `checklist`

Optional later kinds:
- `approval_request`
- `bot_run`
- `reference_note`

## Recommended Data Model

## 1. Do not make `Goal` and `Project` new `task_type` values

That would keep:
- hierarchy coupled to execution behavior
- strategic objects mixed into Today
- rules, icons, filters, and compat surfaces overloaded again

Instead:
- `Task` links upward to `goal_id`, `project_id`, and optionally `routine_id`
- child execution remains `parent_task_id` only when there is real task decomposition
- checklists stay inline JSON for procedure execution

## 2. Split mutable bot/human data into independent sandboxes

SQLite/libSQL means "JSONB" in practice becomes JSON text columns.

Recommended task sandboxes:
- `strategy_payload`
- `integration_payload`
- `checklist_state`
- `agent_context`
- `proposed_artifact`

Recommended family clocks:
- `updated_at` for core task fields
- `checklist_updated_at`
- `agent_context_updated_at`
- `proposed_artifact_updated_at`
- `orchestration_updated_at`

Reason:
- human checklist edits and bot scratchpad writes are different concurrency domains
- separate columns + family clocks allow safe auto-merge when edits are disjoint

## 3. Add explicit orchestration primitives

Minimum fields on `tasks`:
- `owner_type`: `human | bot`
- `orchestration_state`: `idle | working | blocked | pending_review`
- `handoff_state`: `idle | agent_working | engine_processing | blocked_needs_human | pending_human_review`
- `locked_by`
- `locked_at`

Add append-only `task_audit_ledger`:
- `task_id`
- `actor`
- `actor_type`
- `action`
- `payload`
- `created_at`

## Answer 1: Schema Addition Strategy

**Question:** How do we update the current schema to support `owner_type`, `orchestration_state`, and the JSON sandboxes without affecting the overall app?

### Recommendation

Add the new orchestration fields to `tasks`, but keep them narrow and low-coupling:

- `owner_type`
- `orchestration_state`
- `handoff_state`
- `locked_by`
- `locked_at`

Add JSON text sandboxes as separate columns, not one catch-all metadata blob:

- `strategy_payload`
- `integration_payload`
- `checklist_state`
- `agent_context`
- `proposed_artifact`

Add independent family clocks:

- `checklist_updated_at`
- `agent_context_updated_at`
- `proposed_artifact_updated_at`
- `orchestration_updated_at`

### Why This Minimizes App-Wide Impact

- Query hot paths still use flat indexed columns for status/ownership/locking.
- Human-readable fields stay flat.
- Only specialized flows parse the JSON columns.
- Existing task reads can ignore new columns until each UI surface is updated.
- The audit ledger lives beside tasks, not inside them.

### What Should Not Be Done

- Do not pack everything into `framework_payload`.
- Do not create one mega `metadata` JSON field.
- Do not model bot behavior only through labels or comments.
- Do not use `owner_type` as the only handoff signal.

## Answer 2: Offline Sync Collision Strategy

**Question:** How will injecting JSON sandboxes impact `sync-engine.ts` for offline PWA users? What happens if a bot updates the scratchpad via API while a human edits the task checklist offline?

### Current Risk

The current offline model is row-level and minimal:
- small `OfflineTask` shape
- queue payload as raw JSON string
- deduplicate updates by entity
- resolve conflicts with last-write-wins

That is unsafe for:
- checklist edits
- bot scratchpad writes
- proposed artifact staging
- lock state transitions

### Safe Merge Strategy

Use **field-family-aware optimistic merge**, not whole-row overwrite.

#### Families

- `core`: title, description, status, due date, assignee, priority
- `checklist`: checklist items/progress
- `agent_context`: bot scratchpad/resume cursor
- `proposal`: proposed artifact / staged output
- `orchestration`: owner, handoff, locks, review state

#### Queue Payload Shape

Each offline update should enqueue:
- `task_id`
- `base_updated_at`
- `changed_families`
- `patch`
- optional `base_family_timestamps`

#### Merge Rules

1. If server changed no family touched by the client:
- apply patch
- preserve remote changes in untouched families

2. If client and server changed disjoint families:
- auto-merge
- bump the touched family clocks only
- append ledger event `auto_merged`

3. If both changed the same family:
- do not silently discard either side
- create conflict result
- set `handoff_state = pending_human_review`
- preserve remote as current
- store local attempt in `proposed_artifact` or conflict payload
- append ledger event `conflict_escalated`

4. If task is actively locked by another actor:
- reject offline replay into `blocked_needs_human` or `pending_human_review`
- allow explicit human force-takeover later

### Concrete Example

Bot online:
- updates `agent_context`
- bumps `agent_context_updated_at`

Human offline:
- checks checklist items
- queues `changed_families = ["checklist"]`

Replay result:
- same task, different families
- safe auto-merge
- no human review needed

### Required Engine Changes

- expand `OfflineTask` to include family timestamps and orchestration fields
- stop deduplicating all updates into one opaque row payload
- replay against `/api/tasks/[id]`, not `/api/v1/tasks/:id`
- return structured conflict payloads, not just whole server row replacement

### Critical Finding

The current offline engine points to `/api/v1/${op.table}`.
This repo has:
- `GET /api/v1/tasks`
- no general `PUT /api/v1/tasks/:id`
- optimistic locking only in `/api/tasks/[id].ts`

So bot-aware offline sync is not safe until the offline layer is switched to the canonical task API.

## Answer 3: Integration Translation Strategy

**Question:** How do we elegantly flatten incoming Vikunja/Trello subtasks into our new JSON checklist array within `todo-bridge.ts` to protect the UI from relational bloat?

### Recommendation

Do **not** make `todo-bridge.ts` own Vikunja/Trello flattening rules directly.

Instead:
- add a shared normalization helper in an integration boundary module
- let each source map into one common `NormalizedTaskIngress` shape
- then let the task domain decide whether the input becomes:
  - a `Task`
  - a `Task + checklist_state`
  - a child `Task`

### Normalization Heuristic

Flatten an incoming external subtask into `checklist_state.items[]` when all are true:

- no independent assignee
- no independent due date
- no comments/attachments worth preserving separately
- no external automation lifecycle of its own
- semantically procedural, not delegatable

Keep it as a child `Task` when any are true:

- independent assignee
- independent due date or scheduling
- comments, attachments, or external references matter
- it may be delegated to a different human/bot
- it needs its own audit trail or handoff state

### Recommended Checklist Item Shape

```ts
type ChecklistItem = {
  id: string
  label: string
  done: boolean
  source?: "meitheal" | "vikunja" | "trello" | "ha_todo"
  externalId?: string | null
  updatedAt?: number | null
}
```

### Where This Shows Up in the Codebase

- `vikunja-compat/store.ts` should normalize external projects and incoming task payloads into internal `Project` + `Task` semantics
- `todo-bridge.ts` should consume normalized task inputs rather than direct row inserts
- UI should only render `checklist_state`, not a separate relational checklist model

### Why This Protects the UI

- card/detail views render one checklist payload shape regardless of source
- no checklist join tables or subtask-only UI branches are needed for simple procedure items
- compat adapters stay responsible for provenance and translation

## Top Technical Risks

## Risk 1: Dual Schema Source of Truth

Files:
- `apps/web/drizzle/schema.ts`
- `apps/web/src/domains/tasks/persistence/store.ts`

Risk:
- changing only Drizzle will create a false sense of completion

Risk:
- semantic rename without a coordinated sweep will leave contradictory behavior

Mitigation:
- one hard-cut execution phase
- replace hierarchy assumptions everywhere
- introduce `task_kind` deliberately rather than mutating `task_type` in place

## Risk 3: Offline Contract Is Currently Wrong for Rich Sync

Risk:
- current engine replays to `/api/v1/tasks` and cannot safely merge bot/human edits

Mitigation:
- move offline replay to `/api/tasks`
- queue patch families and family clocks

## Risk 4: `board_id` Semantics Will Fight `Area` and `Project`

Risk:
- if `board_id` remains the main grouping primitive, either `Area` or `Project` will become a second-class alias

Mitigation:
- decide early whether current boards become projects or a separate area/project presentation layer
- keep translation adapters at the boundary

## Risk 5: Bridge Logic Will Drift If Normalization Is Reimplemented Per Source

Risk:
- HA todo, Vikunja, Trello, Grocy, and bot imports will all invent slightly different task semantics

Mitigation:
- shared normalization function for ingress into the task domain
