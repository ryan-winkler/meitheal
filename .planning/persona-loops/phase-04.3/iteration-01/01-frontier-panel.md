# Frontier Panel - Phase 04.3 Docs Narrative Iteration 01

## Objective

Turn Meitheal's public docs into a coherent product story that matches the current codebase and makes the Home Assistant-native value obvious to a first-time reader.

## 20 Frontier Lenses

| Lens | Recommendation | Decision |
|---|---|---|
| Product story lens | Lead with the household and homelab execution-hub story before feature detail | Accept |
| First-run lens | Show quick install and voice/Assist setup as the shortest path to value | Accept |
| Home Assistant-native lens | Explain why running inside HA matters: ingress, automations, services, sensors, companion flows | Accept |
| Non-developer lens | Replace implementation jargon with job-based capability groupings | Accept |
| Docs IA lens | Use README for the story and direct readers to setup/protocol docs for depth | Accept |
| Accuracy lens | Avoid one global tool count across different agent surfaces | Accept |
| Protocol lens | Separate Astro MCP, HA MCP, A2A, WebMCP, and HA LLM API descriptions clearly | Accept |
| DDD lens | Make the newer hierarchy language primary without hiding compatibility realities | Accept |
| Transition lens | Name legacy Epic/Story, board, `task_type`, and Vikunja terms as compatibility layers | Accept |
| Search lens | Treat SearchHub and the settings shell as headline product capabilities, not buried implementation details | Accept |
| Mobile lens | Highlight PWA and companion handoff as part of the core story | Accept |
| Offline lens | Present offline mode as practical resilience, not buzzword filler | Accept |
| Trust lens | Emphasize local-first behavior, exports, backups, and no-cloud requirement | Accept |
| Accessibility lens | Keep accessibility claims grounded in shipped behavior, not aspirational language | Accept |
| Proof lens | Refresh screenshots to reflect the newer dashboard and settings shell | Accept |
| Contributor lens | Align AGENTS and skill identities with the new public story | Accept |
| KCS lens | Keep protocol and setup docs synchronized with the README story | Accept |
| Maintenance lens | Create a repeatable docs phase and persona-loop trail for future refreshes | Accept |
| Competitive lens | Explain how Meitheal differs from plain todo apps and from Grocy without turning the README into a comparison matrix | Accept |
| Release-readiness lens | Note scaffolding and experimental surfaces honestly where needed, especially A2A task persistence and WebMCP | Accept |
