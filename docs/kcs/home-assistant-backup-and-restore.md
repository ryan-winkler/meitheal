# Home Assistant backup and restore

Stable and canary use Supervisor-managed cold backups. Supervisor stops a running Meitheal app before archiving its data and starts it again afterward. The app is unavailable during the snapshot. [Home Assistant app backup configuration](https://contributors.home-assistant.io/apps/reference/configuration/#backups)

Use the Home Assistant backup controls for a database that contains a named Board, Personal Pillar, personal display label, Selected people or Nobody audience, or task location. Changing a restricted audience back to Everyone keeps the database protected from raw download. Named Board access uses `/data/meitheal-board-grants.json` and a transient pending directory (`meitheal-board-grants-pending`). Home Assistant cold backups include `/data/meitheal-board-grants.json` alongside `meitheal.db`, and exclude only `*.log`, `*.tmp`, and `meitheal-board-grants-pending`. Because `meitheal-board-grants-pending` is excluded and App shutdown does not wait for marker publication after a committed grant write, confirm Meitheal stopped cleanly with `meitheal-board-grants-pending` empty (or restart briefly to finish publishing any committed pending revision) before creating a Supervisor or manual cold backup; if a post-`0016` archive taken during that window restores with a mismatched revision (`503 continuity_locked`), recover using the stopped-App operator checkpoint procedure below. A live interruption can finish publishing an exact matching committed revision from the pending directory. On post-`0016` (`schema_version >= 26`) installations, a missing, invalid, or mismatched revision keeps governed work closed (`503 continuity_locked`), including Household reads, writes, and delivery, until recovered with the matching backup or offline operator checkpoint procedure. Existing non-empty local Meitheal databases before `0016_ordinary_boards.mjs` (`schema_version < 26`) automatically enroll or recover their grant revision during startup when neither a conflicting marker file nor an unresolved pending entry exists on disk.

## What is protected

The app backup contains Meitheal's persistent `/data` volume and Supervisor app options. This includes `meitheal.db`, its SQLite WAL and shared-memory files when present, and the committed `/data/meitheal-board-grants.json` marker. The app excludes disposable `*.log`, `*.tmp`, and transient `meitheal-board-grants-pending` files. Keep all SQLite recovery files together.

A Meitheal-only backup covers the selected app. Home Assistant Core settings, separately managed integration files and browser-local state have separate backup paths. Supervisor backs up registry image metadata for a prebuilt app and requires the matching image during a restore to a different version or host. [Home Assistant Supervisor backup implementation](https://github.com/home-assistant/supervisor/blob/2026.10.5/supervisor/apps/app.py)

Live Board event streams recheck the connected user's current access before delivering an update. While continuity is locked, new stream requests return HTTP 503 and existing streams withhold updates. After restoring a verified checkpoint, reopen the Board to load its current state.

Task and Settings downloads are portable exports. The Settings export includes eligible preferences, shortcuts, layouts, rules and framework overrides. Enter credentials separately when moving the exported settings to a fresh installation.

The **Raw DB** action under **Settings → Backups & Reset → Data Portability** is available to Home Assistant's verified current owner. The raw download is available for databases without personal or restricted records. Supervisor backups retain Personal Pillars and Principles under the storage operator’s custody. A restore keeps Personal Pillars tied to their original Home Assistant user IDs. A user missing from the restored Home Assistant instance has no Personal Pillar access. It copies a consistent snapshot of the local SQLite database, including writes already committed in the WAL. It needs enough free space for one temporary copy on the database volume. Only one download can prepare or read that copy at a time. Retry after the first finishes or is cancelled. If the app loses power during a copy, a private `.meitheal-export-*` folder may remain beside the database. With Meitheal stopped, remove the incomplete temporary folder before retrying.

Confirm the download in Settings. The browser submits a native form and saves the streamed attachment. If the app has restarted or Settings has been open for more than 15 minutes, refresh Settings before retrying. The form is tied to the signed-in administrator and direct links to the download endpoint return a method error.

Keep the download private. Use the Supervisor backup to recover the complete app, including its options and other files in `/data`. For a remote database, use its host's backup tools. [SQLite online backup](https://www.sqlite.org/backup.html)

The download needs an online connection to Home Assistant Core. Meitheal checks the administrator’s current account before creating a snapshot. If Core cannot verify access, wait for it to reconnect and retry. If an edited download URL fails, open it again from **Settings → Backups & Reset → Data Portability**. Reload Meitheal and activate the app update on browsers that used an older build to remove old cached export URLs.

## Automatic startup database snapshots

For an existing nonempty local SQLite database, the migration runner saves a consistent snapshot before applying SQL changes. If you start the web server directly, its first schema initialization takes the snapshot instead. The packaged launchers coordinate so each successful startup makes one backup attempt.

The snapshot includes committed WAL data. Meitheal publishes the completed file as `backups/meitheal-<timestamp>-<unique-id>.db` beside the database and keeps the five newest named snapshots. If it cannot complete a snapshot, it logs the failure and continues startup. Fresh, in-memory and remote databases skip this local backup. Use a verified Supervisor backup for the complete App recovery point.

## Create a backup

1. Open **Settings → System → Backups → Backup now → Manual backup** in Home Assistant.
2. Select the installed Meitheal app, name the backup and choose an approved location. Confirm the app and version in the completed backup details.
3. Keep an off-device copy and its emergency kit available to the operator. App data and options can include private household information or credentials.
4. If the app was running, confirm it returns to service. Open the Meitheal ingress page and confirm `GET /api/health` reports a healthy database.
5. Keep `/data/meitheal-board-grants.json` inside the cold App backup. For separate off-device operator custody outside the App archive, you can also capture a checkpoint as described in [Capture and refresh](#capture-and-refresh).

## Checkpoint a legacy installation before upgrading

An installed app can still use the former hot backup configuration even when the repository has a newer cold-backup manifest. A checkpoint can flush committed WAL frames and still allow a new write while an archive is being created.

1. Record the installed channel, app slug, version and exact image digest. Preserve access to the prior image, including its tag and architecture. If the registry image is unavailable, retain an off-device image copy and rehearse a compatible rollback before proceeding.
2. Use an approved outage window. Stop only Meitheal in **Settings → Apps** and confirm it is stopped. Create a manual backup selecting only that installed app. Download and verify the backup and recovery material before proceeding.
3. For normal Home Assistant updates from `v0.0.2` (`schema_version < 26`) without a conflicting marker on disk, the upgraded App enrolls and migrates automatically on startup. Keep the manual backup through the upgrade. For older conflicting-marker recovery or explicit offline custody verification, continue with [verified legacy upgrade](#first-installation-and-a-verified-legacy-upgrade). For an ordinary current installation, resume it if it was running before capture and confirm ingress and health. Home Assistant's optional update backup provides an additional recovery point.
4. Check which installer owns any existing Meitheal custom integration. An app upgrade can leave a legacy `custom_components/meitheal/backup.py` behind in a previously copied integration directory. Verify the installed component has been updated through its owning installation path before accepting the backup behavior. Check Core logs for calls to the old backup endpoints. Keep an integration rollback copy if separately upgrading the integration.

## Restore and verify

Restore only the matching Meitheal app from the selected Home Assistant backup. The stable and canary apps have separate data volumes. Stop Meitheal before checking recovery authority. A backup or matching historical image/data pair does not establish which permissions are current. For governed or unknown snapshots, follow [current checkpoint recovery](#recover-governed-access-from-a-current-operator-checkpoint) before starting any image. Keep an incapable predecessor stopped; use the qualified policy-aware image for an isolated denial rehearsal. Preserve the prior image/data together as historical rollback material, not as permission to reopen work.

Use an App-only backup captured while the App was already stopped for the [governed restore procedure](#restore-without-reopening-historical-permissions). Supervisor can start the archived image automatically after restoring a backup captured while the App was running. Older archives may also contain their original grant marker. Recover those files offline or in an isolated, disposable Home Assistant instance. This applies to every Board, including the editable example.

1. Wait for Supervisor to finish and verify the exact restored app version and image.
2. Confirm whether the backup included `/data/meitheal-board-grants.json`. Before starting any restored cold backup — whether a pre-`0016` markerless archive (even on a fresh host with no marker on disk) or a governed backup containing matching `meitheal.db` and `meitheal-board-grants.json` files — confirm against current operator custody that no later grant revocation or Board lifecycle change superseded the snapshot, because an older snapshot or matching database/marker pair cannot establish current permissions on its own. Once verified, start the App for matching backups or clean pre-`0016` archives and check ingress and `GET /api/health`. When performing out-of-band operator custody recovery or restoring a post-`0016` snapshot missing a matching marker, keep the app stopped until [Recover governed access](#recover-governed-access-from-a-current-operator-checkpoint) verifies authority and restores the matching marker; a missing or mismatched post-`0016` restore stays locked (`503`).
3. Verify a known task, relation and setting match the backup point.
4. In the disposable Home Assistant devcontainer, run `PRAGMA integrity_check` on a restored copy of `/data/meitheal.db`. Require `ok` and verify the migration and app logs.

If the restored app cannot start, preserve the backup and check Supervisor and app logs. Verify that the old image can be retrieved and the backup contains the selected app. If database integrity fails, keep the restored app stopped and use the last verified backup.

## First installation and a verified legacy upgrade

A genuinely new local database enrolls its initial access revision during the creating startup process. The migrator prepares the pending marker journal, commits the database and publishes `/data/meitheal-board-grants.json` before the separate web server starts. Restart reads that persisted matching state. Existing empty (`0`-byte) files and unknown non-Meitheal SQLite files cannot acquire first-installation authority. Existing non-empty local Meitheal databases from `v0.0.2` or pre-`0016` releases (`schema_version < 26`) automatically enroll or recover their grant marker during startup migration to schema `28` when no conflicting marker file or unresolved pending journal entry exists on disk.

An existing post-`0016` installation with a valid current epoch and matching `/data/meitheal-board-grants.json` upgrades normally. A pre-`0016` snapshot replayed alongside a conflicting existing marker on disk stays `503 continuity_locked`, and requires a stopped, independently verified **current** checkpoint via `enroll-legacy-continuity.mjs` or recovery of its matching marker. See [the initial continuity decision](../decisions/0026-board-continuity-enrollment.md) and [the backup and pre-0016 continuity update](../decisions/0030-home-assistant-backup-and-upgrade-continuity.md).

The supported offline operator entry point is:

```sh
node apps/web/scripts/enroll-legacy-continuity.mjs \
  --database ABS_DB --marker ABS_MARKER \
  --custody-directory ABS_EXTERNAL_PRIVATE_DIR \
  --manifest ABS_MANIFEST --archive ABS_COLD_ARCHIVE \
  --installation ID --app-slug SLUG \
  --image IMAGE@sha256:DIGEST --source FULL_40_HEX_SOURCE
```

These arguments identify an already verified current checkpoint; they do not certify it. Run only while the App is stopped, using the qualified source/helper and the App data owner. On Supervisor, run the helper from the exact qualified continuity-aware image, with access limited to the stopped App data volume and the protected operator custody directory; this is an explicit operator job, not a new persistent App mount. Record that helper image/config and source separately from the original checkpoint image/source. The manifest and the `--image`/`--source` arguments identify the predecessor that produced the verified cold checkpoint; do not relabel it as the helper image. The independently verified current attestation must bind that original checkpoint identity. The helper is a trusted execution tool, not evidence that the checkpoint is current. Keep that custody directory and its consumed records durable across attempts. Keep the private manifest and current attestation outside App data and outside its Supervisor archive. The exact immutable image/source and installation must agree with the independently recorded Core-owner and stopped-App proof. Verify the original archive scope, extraction, integrity and cold database file family before creating the attestation. Never generate a current attestation from an arbitrary restored database.

The manifest has kind `meitheal-current-legacy-checkpoint-v1` and fields `checkpointId`, `installationId`, `appSlug`, `image`, `source`, `archiveSha256` and `databaseFamily`. The file family records SHA-256 values for `database`, `wal`, `shm` and `journal`; absent sidecars are null, and an unresolved rollback journal is rejected. The protected custody `current.json` has kind `meitheal-current-continuity-attestation-v1`, the same checkpoint/identity/image/source, exact `manifestSha256`, `state: "current"`, `coreOwnerVerified: true`, `appStopped: true`, `noNewerGrantOrLifecycleChange: true` and an independent `verificationId`. These assertions belong to the trusted operator's external continuity record.

All operator checkpoint capture, current-attestation publication and supersession operations must acquire the same exclusive lease: create the private directory `<custody-directory>/.continuity-operation` with mode `0700` using no-clobber `mkdir`, and retain it through their final publication. Enrollment uses that lease from its final current-proof check through one-shot consumption, the SQLite writer and grant publication; it rereads the exact manifest and current-attestation bytes before consumption and again under the writer. Do not replace `current.json` or its manifest while another operation holds this lease. An existing lease makes the operation fail closed. After an interrupted operation, independently reconcile the stopped App, custody records, consumed receipt and any journal before manually removing the abandoned lease; never infer that it is stale from age or automatically retry around it. External capture scripts must implement this protocol before use; upgrading the enrollment helper does not update those scripts.

The command rejects mismatched, foreign, historical, superseded or missing evidence before modifying the database. It durably consumes the one-shot checkpoint ID outside App data before opening or migrating it, verifies the complete original cold file family before SQLite opens it, then rechecks persistent database/WAL bytes under the writer before migration. SQLite may rebuild its already verified shared-memory index or create an empty WAL; the existing committed WAL cannot be dropped or substituted. It then enrolls through the shared journal protocol. A consumed proof cannot be replayed after interruption. A failure before commit needs a newly established current checkpoint; there is no force flag or in-app unlock. This command does not replace recovery of an already enrolled checkpoint from its separately retained current marker.

For the packaged helper, bypass the normal App entrypoint and invoke Node directly as `10001:10001`. Use a networkless one-shot container with only the stopped App data volume and private custody directory mounted. Paths passed to the helper must resolve inside those mounts. Record the helper's raw image configuration digest separately from the original checkpoint and selected runtime image digests.

## Recover governed access from a current operator checkpoint

Home Assistant Supervisor cold backups now include `/data/meitheal-board-grants.json` (and exclude only transient `*.log`, `*.tmp`, and `meitheal-board-grants-pending` files). If an earlier archive omitted the marker or a post-`0016` restore encounters a missing or mismatched marker, recover access using a verified current checkpoint paired with `/data/meitheal-board-grants.json` in operator custody. Do not reconstruct its revision from a restored database row. This procedure needs operator access to the App's local volume; there is no in-app unlock or database import endpoint.

### Capture and refresh

1. Establish continuity while the known current App is running. Verify the current Home Assistant owner through Core and check the expected Board roster, authorized reader and denied reader. A fresh empty installation enrolls through its ordinary owner flow. An existing installation needs its confirmed live upgrade or an independently trusted current checkpoint. A markerless restored database is not proof of first enrollment.
2. Record the App slug, channel, architecture, exact image/config identity and full source revision. Record the actual `/data` mount before stopping; Supervisor can remove its runtime container on stop. Stop only Meitheal and wait for its lifecycle job to finish. Keep Core accounts and other Apps unchanged.
3. Verify the published marker is a regular private file, and that no pending publication journal remains unresolved. Retain a private backup copy of the marker bytes and verify that its revision matches the cold database. Create a stopped-App Supervisor backup selecting only this App, with no Core or folder backup. Keep `meitheal-board-grants.json`, `meitheal.db`, WAL, and shared-memory files together.
4. Download the archive off-device. Record SHA-256 checksums for the archive, marker and cold database file family, and bind them to the installation and exact image. Independently extract the archive, verify SQLite integrity and foreign keys, the same database revision, App-only membership, and pending journal exclusion. Retain the matching image; a tag alone can disappear or change.
5. Publish the verified checkpoint as current in a protected continuity record outside the Supervisor archive, keeping earlier records historical. Resume the exact App and recheck reader/denied-reader parity.

**Every committed grant or Board lifecycle change makes the previous checkpoint historical.** Refresh using these stopped-App steps after the change. Record a known newer change even if checkpoint capture is interrupted. If host loss occurs before refresh and current continuity cannot be independently established, recovery stays locked. An old checkpoint, a matching old database/marker pair, a timestamp or the last saved pointer cannot establish currency by itself.

### Restore without reopening historical permissions

1. Record the actual local volume while the container exists, then freeze writers and stop only Meitheal. Hold the [shared custody lease](#first-installation-and-a-verified-legacy-upgrade) across the final custody proof, restore and marker publication. Wait for Supervisor to be idle. Establish that the retained checkpoint's authority is independently current against the stopped live authority and protected continuity record. Verify the retained archive and recorded file hashes separately. Ordinary work since capture may change the live database while its authority still matches. Before replacing a readable volume, retain and verify a separate stopped App-only backup and its separately retained marker so those later writes can be recovered. Require the same installation and App slug, exact checkpoint image identity and separately retained marker. Preserve the stopped state and evidence when these checks fail.
2. Before restoring, verify from the archive metadata and members that Meitheal was already stopped at capture and that only the intended App is present. Require that the archive excludes pending journals (`meitheal-board-grants-pending`). Restore only that App and its data. Wait for the job to finish, then confirm in Supervisor that the App stayed stopped while validating external custody. If the App started unexpectedly when verifying an older excluded-marker archive, stop it and preserve the logs and restored files for investigation.
3. Before starting, confirm that the selected continuity-aware package can open the archived schema. Use a receipt from disposable Supervisor with the exact candidate digest and the retained archive or an equivalent identified schema and migration ledger. The receipt records the expected migrated schema, lock result and authorized reads. Check the selected package's architecture, immutable registry digest, raw image config and full source. If the restored package cannot enforce continuity, keep it stopped and select the qualified successor through the same App's Store entry. Refresh the Store, confirm it offers the exact version, and use the normal Supervisor update action on that stopped App. Wait for the update job to finish. Confirm the same App slug and data volume, the exact selected package, and the stopped state.
4. Through the recorded local volume, verify the exact restored database file family against the archive. With the lease still held, recheck that the private custody record and marker checksum still match, the App remains stopped, Supervisor is idle, and the pending journal is clear. Check any restored `/data/meitheal-board-grants.json` against the independently current custody marker bytes: if they match, retain the restored file in place; if the marker destination is absent, publish the retained current marker bytes with no-clobber/no-symlink handling, owner `10001:10001`, mode `0600`, and file plus parent-directory durability. Abort publication and keep work stopped if a mismatch or unresolved journal exists. Start the selected package and record the actual running source/config/schema, integrity, protection, authorized reads and denied readers. Any subsequent grant or lifecycle mutation requires a fresh checkpoint.

In disposable Supervisor, prove both the missing-marker lock and an older database paired with the independently current newer marker remain closed. Then prove the matching latest checkpoint restores only its current permissions. Keep failed and successful receipts separate. Portable re-certification after unknown continuity is a separate owner-approved procedure.

## Move data between Store repositories

A different repository URL creates a different internal App ID and data volume. A matching-App Supervisor restore is not a database import into that new ID. Settings JSON also omits tasks and protected credentials; there is no in-app SQLite import endpoint. This one-time transfer requires an operator with access to the App's local volume.

Copying the source database alone does not transfer its independently current Board authority. The source marker must remain in protected custody with its source installation, image and current cold checkpoint. The target has a different installation/App slug, so the same-installation recovery procedure above cannot authorize publishing that marker there. Governed access stays locked. Cross-installation re-certification is not implemented in this runbook; complete a separately specified and owner-approved transfer procedure before enabling protected work. Do not relabel a source checkpoint as a target checkpoint or infer new authority from the moved database.

Rehearse the complete transition in a disposable Supervisor before changing the installed Canary. Isolate outbound network access before starting restored data or applying old App options: saved integration and logging endpoints can be contacted during startup or a health request. Limit the rehearsal browser to fixture services as well. Preserve stored values and verify isolation with a disposable control endpoint, without probing real saved URLs.

1. Keep the old App's complete backup, recovery material and exact image available. Select the complete database to retain. Work on a copy with its WAL and shared-memory files; use SQLite's backup API to produce a consistent standalone database. Require integrity and foreign-key checks, and privately record the original tasks and setting values. Keep the immutable source recovery files. [SQLite backup API](https://www.sqlite.org/backup.html)
2. Install only the new Canary. In the isolated rehearsal, start it with empty data and default options, and record its exact image and actual `/data` mount while its container exists. Then stop it through Supervisor. Installation alone does not create the container, and Supervisor stop normally removes it; inspect the mount before stopping. Confirm the App is stopped and no lifecycle job is still running. [Supervisor lifecycle](https://github.com/home-assistant/supervisor/blob/2026.10.5/supervisor/docker/app.py)
3. Through the recorded mount, retain any target database, WAL and shared-memory files together and move them away from the active database names. Keep the new `options.json` under Supervisor control. Place the normalized database in a temporary file on the same local volume, verify its checksum, set owner and group to the packaged service account (`10001:10001`) with mode `0600`, and rename it to `meitheal.db`. Never leave an old target WAL beside a replacement database.
4. Compare archived App-option names and types with the new manifest. Apply the complete intended compatible configuration through **Settings → Apps → Meitheal Canary → Configuration** or Supervisor's options API; record incompatible options for an explicit decision. Database settings and Supervisor App options are separate. Do not copy the old `options.json`, because Supervisor validates and regenerates it at startup. [Supervisor options API](https://github.com/home-assistant/supervisor/blob/2026.10.5/supervisor/api/apps.py#L315-L357)
5. Check migrations, database integrity and foreign keys in the isolated target. A database moved without independently certified target authority must remain recovery-locked; do not treat healthy storage as permission to serve its tasks or settings. Compare retained data offline against the selected source and account for schema conversions. Enable normal App acceptance only after a separately approved target re-certification procedure exists and passes.
6. Verify any separately managed Core integration's endpoint, authenticated actions and saved ingress links. Rehearse recovery with the matching prior App and data while that recovery path is still available. Keep network isolation throughout the rehearsal.

After the qualified Green transition passes the same acceptance, create and verify a backup matching the new App ID. Remove obsolete discovery entries only when no installed App depends on them. Retain the selected source checkpoint until the new recovery point is proven. This procedure does not replace the physical Green performance or installation gates.

## Verify the draft storage migration

For an upgrade from schema 14, take an App-only checkpoint and use a disposable copy to verify schema 15. Confirm SQLite integrity and read a known ordinary task after the app starts. Run `node scripts/migrate.mjs --check` from `apps/web` with the fixture database URL to verify the draft tables and receipt index. Keep the original checkpoint available for a rollback to the previous App. When checking post-upgrade task creation, verify concurrently created and duplicated tasks each return a distinct ticket number that matches the task details.

When draft capture is enabled, make a second App-only checkpoint with a saved draft from each of two temporary members. Save a later test draft change and restore the checkpoint. Confirm each member sees only their earlier draft and the later change is absent. Check both the App version and database integrity before testing ingress. A private draft and its publication receipt are part of the App database, so apply the same custody rules as for the full database download.

## Tier 2 acceptance

In the editor-managed Home Assistant devcontainer, seed a task, related data and settings. With Meitheal running, create a backup and record the stop before archiving and the restart afterward. Use that archive only for the backup lifecycle check.

For data rollback acceptance, capture a separate independently current App-only checkpoint with Meitheal already stopped. Retain the marker separately. Resume and make one ordinary test write that does not change authority, then stop Meitheal and capture the outgoing fallback backup and marker. Restore the older cold archive and publish the still-current marker through the stopped procedure. Verify the first write survives and the later test write is absent. Independently confirm that the outgoing checkpoint's authority is still current before restoring it and its separately retained marker. Verify both writes and the same authorized and denied reader results. Keep both restore receipts.

For authority recovery, use synthetic Boards, accounts and integration configuration in the disposable Supervisor. Hold one historical stopped checkpoint across a real Board grant or lifecycle change, then capture the newer independently current stopped checkpoint. Before either denial start, verify the policy-aware package and its archived-schema compatibility using the same stopped selection above. Recheck package identity after reapplying any archive. Because a current historical cold archive now includes its matching historical marker, keep the App stopped after restoring it: delete the restored historical marker before testing the missing-marker `503` denial, and replace it offline with the independently newer marker before testing the mismatch `503` denial, verifying each marker state before startup. Use authenticated Board/task reads and a task write, a count request and a database export. Require HTTP `503`, private, no-store headers, no private values and unchanged governed rows. Reapply the matching current cold archive, verify the selected package, verify or publish only the matching current marker and confirm that an authorized reader can open the same Board whose revoked reader is now denied. Record predecessor and recovery image digests and sources, the same App slug and data volume, both authority revisions, archive checksums and pending journal exclusions, the stopped state across restore, SQLite integrity, and ingress results.

Before updating the Green, rehearse the older app and data rollback on a disposable Supervisor. A locally tested archive proves file recovery. It takes a Supervisor rehearsal to verify the lifecycle and a Green run to verify device acceptance.

Include a stopped archive of a different representative predecessor version. Rehearse selecting the qualified successor through the same Store App while stopped. Record the Supervisor update, the same App slug and volume, the before and after package identities, preserved cold database files, stopped state throughout, and subsequent controlled startup and scoped reads.

Schema 24 adds raw-download protection for Nobody audiences and prevents changing or clearing a generated Routine occurrence's saved date when one is present. It upgrades existing schema 23 data in place and keeps the previous migration ledger entries. Use the matching App and data backup when restoring an earlier schema.
